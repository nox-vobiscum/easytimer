**Status:** Strategic direction agreed; the native Schema-2 domain, persistence,
runtime-transition, UI-neutral Template Library read/create/update/delete boundary
and Planner-facing draft/outcome service, plus a passive Schema-2 JSON portability
contract and UI-neutral native Session-launch orchestration boundary, are
implemented and verified
locally but not released. The boundaries
map prepared Editor data to native Templates and use the lock-protected Editor
Store without exposing a second library. Public Editor UI and unified-library integration, remaining
lifecycle/archive workflows and the Facilitator Panel remain pending.
**Priority:** High / Near-term. Every subsequent implementation slice requires
separate explicit Product Owner approval.

**Public Planner preparation:** The existing public V1 Planner now isolates its
draft mapping and Save/Delete/import aggregate preparation in `planner-v1.mjs`.
These pure V1 operations retain the released data shape; they are not a native
adapter. The Planner still owns UI state, asynchronous I/O guards, navigation,
backup and launch callbacks. Native UI integration remains pending. The new
module is packaged and precached with the current unreleased PWA asset references.

**Native Template draft editing foundation:** `editor-template-draft.mjs` edits
the existing native Planner Service draft envelope without V1 materialization.
It provides isolated field edits and phase insertion/removal/final-position
reordering while retaining Template/phase identities, revision bases and all
unrelated planning fields. New phases use explicit caller-provided IDs, empty
titles, ten-minute duration and neutral categories. Invalid field contents stay
in the draft until an explicit Planner Service Save validates them through the
native domain. Discarding a draft has no persistence effect. This module has no
UI, storage or lifecycle operations and is not imported by the public Planner;
native presentation and the public cutover remain pending.

**Internal native phase field group:** `editor-phase-fields.mjs` provides title,
minute-duration and category inputs for one stable phase ID, using the existing
`editor-template-draft.mjs` operations. The host supplies its current native
Planner Service draft through `getDraft`, adopts edits synchronously through
`onDraftChange`, and may call `refresh`, `setLanguage` and
`showValidationError` after explicit native validation. No draft or library is
cached, and the component never saves. Its phase-row and expandable category
detail styles are part of the central `css/styles.css` stylesheet. Escape
collapses details and restores focus. Language changes retain the active input
and selection; invalid minute text stays in the draft for the native Save
validator. This is an internal presentation boundary only, not the final phase
details design. Name/transition and Rundown metadata controls, Notes/Resources
overlays and insertion/removal/reorder UI remain pending. No public Planner
import, packaging or Service Worker cutover is included.

**Internal native Template import contract (unreleased):**
`createNativeTemplateImportService({ writer, createId })` in
`editor-template-import.mjs` separates `prepareImport(text,
expectedAggregateRevision)` from the explicit `persistImport(candidate)` decision.
Preparation uses the existing strict, versioned portability parser and its
10 MiB UTF-8 limit, reads/writes nothing and returns `prepared` with an isolated
candidate. Only an individual `editor-template` document is accepted. Its fresh
Template ID must differ from the source ID; revision starts at 1. All planning
fields and phase IDs are retained: phase uniqueness is scoped to each plan, so
there are no cross-Template phase references to remap. ID collisions are rejected
without regeneration. The candidate retains the caller's observed aggregate
revision; persistence checks it under the existing exclusive Store writer lock,
inserts once and returns `confirmed`, the imported `templateId` and the full
confirmed `record`. No existing Template, Execution or ACTIVE runtime is changed.

Failures return structured `error` outcomes and preserve a valid candidate.
Unconfirmed/mismatching readback, or a LockManager rejection after the insertion
callback ran, returns `uncertain` with a caller-retained `reconciliation` ticket
containing the candidate and complete source/target records. There is no pending
registry, automatic retry, merge or second ID allocation. `reconcileImport(ticket)`
validates those records against the insertion and performs only `writer.read()`:
the exact target is `confirmed`, the exact source is `absent`, and any other
snapshot or failed read is `unresolved`. Absence describes the current unchanged
source snapshot, not proof that a write never occurred. Unresolved outcomes retain
the ticket; the caller must retain it until an explicit resolution. Tickets are
not durably stored and do not provide crash recovery of an unfinished import.

Execution documents and backups, even valid ones containing ACTIVE runtime, are
not persistent imports. Passive parsing/export remains supported, but Execution
identity/checkpoint import policy and full-backup replacement/ownership policy
require separate review. No restore, activation, timer ownership claim, V1
conversion, public import UI or public Editor cutover is included.

**Internal Planner integration boundary:** The UI-neutral native Planner service
loads copy-isolated Template Library snapshots, prepares complete isolated create
or edit drafts, and carries the captured aggregate and Template revisions into
the existing lock-protected native operations. Successful writes return a fresh
confirmed library snapshot; rejected writes return structured error information
and preserve the unsaved draft without merge, retry or overwrite. The service
does not cache library state, access V1 storage or change the public Editor,
Session Picker or timer UI. Their cutover remains separately reviewable and
requires explicit approval.

**Internal Session launch boundary:** Native launch orchestration first creates
one independent PLANNED Execution through the existing locked Store writer and
then activates that same Execution into READY through the existing Runtime
Bridge. Confirmed planning is never rolled back or repeated merely because
activation fails. An unconfirmed planning write returns its stable Execution ID
for explicit read-only observation; an unconfirmed activation remains subject to
the Runtime Bridge's existing pending-operation reconciliation. READY has no
Attempt and does not count time: only a later explicit START may create the first
Attempt and begin the authoritative Session clock. This boundary does not yet
change the public Session Picker, Direct Launch or Editor UI.

**Binding EDITOR-001 data decision:** There are no historical user Rundowns that
require migration. New templates and independent executions are created directly
as native Schema-2 objects in the Editor Store aggregate. No V1-to-V2 conversion,
historical compatibility import, dual-library migration, startup migration or
migration wizard is required or authorized. The released V1 implementation may
remain temporarily and must keep working until separately approved replacement;
that regression requirement does not imply data migration. Future JSON
import/export for the new model is a separate contract, not a historical V1
migration path. Revisit this decision only through an explicit Product Owner
change.

## Purpose

Make easyTimer more useful for preparing and facilitating real workshops while keeping the timer itself simple, reliable, and visually quiet.

**Product principle:** The facilitator leads the event; easyTimer supports the facilitator rather than replacing their judgment. Prepare a useful plan in the Session Editor, adapt it to what happens in the room, and use the Session Timer and the optional facilitator's cheat sheet as tools—not as authorities over the workshop.

**Feature-selection principle (KISS and concrete user value):** Do not build a feature merely because it is technically possible or interesting. Add it only when it addresses a real facilitator/user need and offers a concrete benefit that justifies the added UX, maintenance and reliability complexity. Deliberately omit or defer features without a convincing use case; prioritize a straightforward, comprehensible experience over speculative extensibility. This is a decision filter, not a ban on future ideas.

A rundown is the **result of planning with the information available at planning time**. It **can be a script (Drehbuch)**: when the prepared sequence fits the actual workshop, the facilitator can follow it **exactly as planned**, phase by phase. Equally, it is a guide that the facilitator may deliberately adapt if the actual group, discussion or circumstances require a different course. Neither the plan nor a timer/timebox ending has authority over the facilitator's judgment. Preserve deliberate user decisions, clear records of what actually happened, and the previously agreed protection of completed phases.

**Terminology guidance for future About/FAQ copy:** Avoid saying that a rundown is *not* a script. Instead, explain that it **may be followed as written, but is not an inflexible mandate**; adapting it is an option, not an obligation. easyTimer supports facilitation rather than dictating it.

This is a focused evolution of easyTimer, **not** an attempt to recreate SessionLab or build a general workshop-management platform.

## 1. Session Editor — preparation workspace

Give the Session Editor more space and a clearer identity as a first-class feature rather than a compact settings panel. Keep the default workflow approachable; richer details should be available on demand.

**Editor layout decision — expandable phases:** Use a compact phase list with on-demand expandable details (accordion pattern), not a permanently split list/detail layout. Responsive behavior is a high priority, including practical editing on mobile devices. Optimize for typical team days and workshops with roughly 10–12 units rather than complex training schedules with 30+ sessions. Keep the collapsed list easy to scan; the details do not need to be visible all the time.

**Editable rundown metainfo — concept addition:** Allow freely editable information associated with the whole Rundown, independently of individual phases (for example workshop goals, a day agenda, general orientation or welcome text). The precise fields and presentation are still open design questions. As a separate *future idea*, this content might later appear as a welcome screen while the Session Timer is READY (for example on a projector as participants arrive), potentially with optional branding such as a company logo. Neither a welcome screen nor branding is part of the current implementation scope; existing timer behavior must remain unchanged.

### Phase detail disclosure — agreed UX direction

- Keep the phase list compact and use **expandable/collapsible phase details** (accordion pattern), with responsive/mobile use as a strong consideration. This is intended for typical workshops or team days of roughly 10–12 phases, not large-scale session-planning software.
- Provide **one subtle disclosure button** combining a list/agenda icon with a chevron. The same button both indicates whether optional phase information is present and opens/closes the details.
- **Outline list icon:** no optional prepared information exists for the phase. **Subtly filled/solid list icon:** at least one optional item exists, whether a note, labeled resource link, or another future optional detail. Do not distinguish content categories or counts through additional markers.
- The chevron communicates only expansion state (down = collapsed, up = expanded); the outline/solid treatment communicates only content presence. These two states are independent.
- Avoid alarming colors, notification dots, badges, or extra buttons. Provide a sufficiently large touch target, keyboard operation, and accessible labels/expanded state.
- **Exact placement within the existing phase action area and responsive layout remain open** until evaluated against the real editor UI; do not prescribe button order or positioning at the concept stage.

### Expanded phase content and editing — agreed UX direction

- The expanded phase in the **planning editor** displays **two clearly labeled sections, both visible at a glance**: **phase notes/content** (neutral working UI term: **Notizen**) and **Links & Resources**. The phase notes can include facilitation cues, background information, agenda points or information intended for participants; **do not name or model them as moderator-only instructions**. They belong to the prepared rundown and are distinct from notes captured during the execution. This distinction does not require a third section in the planning editor, nested accordions, file uploads, or a new audience/role permissions system. Final DE/EN UI labels remain open.
- **Notes:** When empty, show a subtle clickable placeholder (“Notiz hinzufügen…” / appropriate English equivalent). Both clicking the preview/placeholder and a separate minimal edit button open the same lightweight text editor.
- Display long notes as a **two- or three-line clamped preview with ellipsis**, not a fully expanded wall of text. Opening the editor reveals the complete content. Support only basic formatting such as emphasis and lists; exact editing and serialization technology remain undecided.
- **Links & Resources:** A single initial section for labeled URLs to websites, boards, presentations, images, documents, videos and other externally hosted material. Each item has display text and a URL; the read view shows only its linked label with a link icon. Clicking the label opens the URL in a **new tab**; a separate minimal edit button edits the entry. When empty, show “Link/URL hinzufügen…” / appropriate English equivalent.
- **Edit actions:** Minimal icon buttons for **Save (checkmark), Cancel and Delete**. Save accepts the current edit into the editor's rundown draft (not an automatic library/template save). Cancel exits editing and restores the last saved state for the item; deleting a note removes its content and returns its section to the empty placeholder. Clicking outside the editor causes **no action**: no implicit save, cancel or delete.
- All these action buttons use a **minimal monochrome icon style**: no signal colors or emoji, with accessible names, keyboard operation, and minimum usable touch-target sizes. Exact placement and responsive spacing remain subject to real-layout review.
- A future richer Google Drive/file integration may justify separating Links from Resources; **not part of the initial version**. Similarly, separately intended **public/presentable vs. moderator-reference notes** are a future concept only. The initial version has no privacy, role or owner-only enforcement; a truly confidential view would need its own later security and access-control design.
- The data contract for basic formatting, storage/validation, JSON import/export, recovery and optional sync requires a separate explicit review; no library or persistence format is selected by this UI decision.

### Responsive overlay editors — agreed MVP UX

- Edit both **Notes** and **Links & Resources** in an overlay instead of expanding editable controls inline within the phase. On desktop, use a spacious dialog; on mobile, use a near-full-screen overlay to maximize usable editing space.
- The Notes overlay exposes the complete note and only basic formatting controls. The Links & Resources overlay can edit **multiple/all labeled URL entries in one session** rather than requiring a separate dialog per link; scroll its contents when needed.
- The mobile layout must adapt to the **actually visible viewport when the on-screen keyboard is open**, keeping the active field usable and actions reachable with scrolling where necessary. Verify actual behavior on mobile devices/browsers; no universal keyboard/viewport behavior is assumed.
- Saving applies the overlay edits to the rundown **draft**, closes the overlay, and refreshes the expanded phase preview. Final persistence remains governed by the existing explicit Rundown Save flow.
- **Cancel/close must guard against accidental loss of edits with a confirmation dialog when there are unsaved changes.** Confirmed discard restores the pre-edit contents; declining the confirmation returns to editing. The earlier rule remains: tapping/clicking outside the overlay does nothing.
- Keep Save, Cancel and Delete as restrained monochrome icon actions with accessible names and adequate touch targets. Exact visual layout and the behavior of Delete within the multi-link overlay remain for later layout/interaction review; this concept does not select an editor library or a serialization format.

### Rundown library: templates and independent executions — agreed product direction

- Distinguish **reusable templates** from **individual workshop rundowns / executions** in the user's library. A user may create and deliberately edit templates, then prepare a separate workshop-specific rundown from one (with or without customization). Starting an unchanged template still creates an **independent execution entity**, not a modification of the original.
- An execution may be planned, active in the timer, deliberately suspended, and eventually deliberately ended. **Archiving is optional:** only executions the facilitator chooses to archive become persistent **Abgeschlossen** historical records in the library; they remain independently available rather than disappearing or being silently merged into their source template. Deliberately ending an execution must not require adding an archive entry. Precise end-without-archive disposal/preservation choices still require UX review.
- Deleting a reusable Template is permitted and never cascades into independent Executions. Their plans, progress and historical source Template ID remain unchanged, including while an ACTIVE runtime exists. This applies to PLANNED, ACTIVE, SUSPENDED and future COMPLETED records.
- A future separately approved operation may use an existing Execution as the source for a new independent cloned Execution. The clone receives a new identity and independent progress; this capability is not implemented by the current Template Library contract.
- A complete native backup includes all currently supported Templates and Executions, including suspended checkpoints and the matching saved runtime for an ACTIVE Execution. Individual Template and Execution exports are supported by the same versioned passive format. An ACTIVE snapshot does not transfer timer ownership, and parsing never restores, activates or persists anything. Public import/export UI and restore policy remain pending. COMPLETED/archive documents remain unsupported until that native lifecycle contract exists; no V1 migration or compatibility import is involved.
- Make the distinction **unmistakable in the UI** through a meaningful icon and/or a short text label; don't rely on subtle iconography alone when template edits might be mistaken for changes to an individual execution. Decide the exact placement against real desktop/mobile layouts.
- An ongoing execution may evolve without retroactively changing completed phases' **structure, timekeeping, progress, or outcomes**. Edits to the **current and upcoming phase structure and timing** must respect already accepted ET-001 decisions 39–43, 45–48, 53–56: completed phases remain structurally/timekeeping-protected; the current phase cannot be deleted/reordered, but allowed title/duration adjustments follow approved timing/conflict rules; upcoming phases may be changed. **Separate informational-content correction (agreed exception):** During an individual execution that has **not yet been deliberately finalized** (including READY, running, paused, suspended), the facilitator may correct or add **prepared rundown/phase information and resource links in the Session Editor, even for a previously conducted phase**, without altering that phase's historic measured time, completion status, order/history, or the immutable original first-Start planning baseline. Such changes update **only that individual execution's latest configured information** and are reflected in its final snapshot if archived; **never automatically change the reusable source template**. Once the entire execution is **Abgeschlossen**, the archived information is read-only under the separately agreed archive rule. Safe execution-aware editing, concurrency and persistence remain prerequisites. **No timer or recovery behavior change is authorized by this concept document.** Runtime-edit implementation remains separately scoped under ST-003.
- Retain the execution's actual changes, phase outcomes, overtime and other relevant history when the facilitator deliberately archives it (precise historical data and retention contract to be designed). **Optionally** allow reusable planning content from an archived execution to be applied to its originating template, but only via an unambiguous, deliberate overwrite confirmation. **There is no template version history, automatic backup or restore flow**: confirmed changes replace the previous template content. Which planning fields are transferable, whether to offer a preview, and exclusion of actual runtime statistics from the template require a separate focused UX/data-contract review.
- Account-free local use and JSON portability remain important. Google Drive, cross-device persistence and any potential server/database service are **separate future architectural evaluations**, not prerequisites or decisions of this library concept.
- **Concise FAQ working copy (DE; wording not final):** „Änderungen an vorbereiteten Informationen während eines Workshops werden nur in der jeweiligen Durchführung gespeichert – nicht in der zugrunde liegenden Vorlage. Beim Archivieren werden diese Änderungen mit der Durchführung festgehalten.“ The distinction is intentional: **saving a live correction is not itself archiving**; if the facilitator instead retains **Nur den Ablaufplan**, the corrected information stays in that planned execution, and if the entire execution is discarded, it is lost. The same applies to **rundown-level and phase-level prepared information**, including corrections to previously conducted phases made **before** deliberate finalization.

- **Deleting a future phase that already contains information (agreed safety prompt):** During an individual execution, deleting a phase that is permitted to be removed under ET-001 must use a **single simple confirmation** when that phase has prepared notes, links/resources, or separately captured Workshop-Notizen (including an unsaved note draft). State plainly that deleting the phase also removes these associated contents from the current execution, name the affected phase, and offer **Abbrechen / Cancel** and **Phase löschen / Delete phase**; cancellation leaves the phase, its contents and current drafts unchanged. Do **not** silently transfer the notes to another phase or add a special notes-inbox, recovery list, or extra deletion wizard. If the phase was part of the immutable first-Start baseline, the separate historical snapshot remains untouched for the agreed archived **Entfernt / Removed** indicator; that baseline is not a backup of a deleted note draft. Deleting a phase from its original reusable source template is **not** implied by editing the individual execution. Exact microcopy and draft/transaction safety remain for implementation review.

### Execution lifecycle, interruption and discard — agreed conceptual rules

- Use **four user-visible library lifecycle statuses**: **Planned** / **Geplant**; **Active in Timer** / **Im Timer aktiv**; **Suspended** / **Unterbrochen**; **Completed** / **Abgeschlossen**. Only one execution may be active in the authoritative Session Timer at a time; **multiple suspended executions may coexist** in the library and be resumed individually later. This is a future capability, not a claim about the currently implemented recovery store.
- Prefer **Im Timer aktiv** to ambiguous **Aktuell** or **Läuft**. When the actual authoritative clock state is reliably available, supplement it with a localized live substatus: for example **Im Timer aktiv (bereit/läuft/pausiert)**, plus accurate overtime variants where applicable. If the substatus cannot be determined confidently (for example due to cross-tab ownership/recovery), display **Im Timer aktiv** alone rather than a stale or misleading claim.
- **Pause** / **Pausieren** and **Suspend** / **Unterbrechen und speichern** are **different operations**. Pause freezes the clock but leaves the execution loaded in the timer. Suspend explicitly saves the execution's current position, phase progress, applicable runtime changes, and timer state, freezes time progression, and **releases the timer for a different session or Quick Timer**.
- **Suspend commits all open Workshop-Notizen drafts (agreed):** Selecting **Unterbrechen & speichern** also saves **every started but not yet saved Workshop-Notizen draft** for the individual execution, including Rundown-wide and notes in any phase, even if another phase is currently selected or the facilitator left several phases open for parallel writing. Save these drafts together with the frozen execution/progress state; **only after all writes succeed** may its lifecycle become **Unterbrochen**, the timer be released and the Panel close. No note-by-note Save clicks or additional confirmation. On any storage/ownership conflict or failed write, **do not suspend, release the timer, close the Panel or discard drafts**; retain the active execution and editable input, and show a clear retryable error. When later resumed, the notes are still present and editable; suspension is not archival. This does not change the deliberate discard/reset or end-without-saving retention rules.
- A suspended execution can be **resumed at the saved point**, including across days, independently of other suspended executions. On reactivation, its timer must initially be **paused/frozen** and require an explicit **Continue** / **Fortsetzen** before any time passes. No missed automatic phase transitions, time accrual or overtime must be caused by the wall-clock interval spent suspended. Preserve the single authoritative clock/ownership model and the applicable ET-001 editing and recovery invariants.
- **Edit a suspended execution directly from the library without activating it in the timer**. The user may open the Session Editor to refine the suspended rundown (for example, shortening an upcoming phase while travelling), save the changes, and leave its lifecycle status **Suspended**. The user must not be forced through **Resume in Timer** to make planning edits, and editing must not interrupt a different currently active execution.
- Keep the **already completed phases immutable**; the suspended current phase and upcoming phases follow the applicable ET-001 in-session editing rules. In particular, the suspended current phase cannot be removed or reordered; allowed title/duration edits must preserve already elapsed time and the frozen pause/overtime semantics. Future phases may be edited/reordered/removed under the existing constraints. Changes during suspension must not run the clock or silently trigger phase transitions; the recalculation rules for shortened current phases, including automatic mode and existing overtime, require an explicit data-contract/test review.
- **Suspended library action priority (agreed, hybrid layout):** For **Unterbrochen**, expose two primary, directly visible actions: **Im Timer fortsetzen / Resume in Timer** and **Durchführung abschließen / End execution** (working copy; actual button naming/layout remains reviewable). **Im Timer fortsetzen** activates the saved execution in the Session Timer with its clock still paused/frozen, requiring a separate explicit Resume to count time. **Durchführung abschließen** opens the **same three-way retention choice** as ending an active execution (archive results / keep latest plan as Geplant / end without saving) **only if the execution was actually started at least once**; a still-never-started READY/suspended execution instead offers only retain-plan or discard, with no archive choice, **directly from the library without loading or restarting the timer**. No suspended-wall-clock time is added to actual duration. For **Im Timer aktiv**, finalization remains available **only from the Session Timer**, not as an extra library row action. All actions preserve safe single-timer ownership and must not silently interrupt an unrelated active execution.
- **Bearbeiten in the contextual menu for Unterbrochen (agreed):** Prioritize **Im Timer fortsetzen** and **Durchführung abschließen** as the two immediately visible actions on suspended execution rows; **Abschließen** warrants direct visibility because it is a major possible next step, without prescribing which visible action must receive stronger visual emphasis. Move **Bearbeiten** to a clearly discoverable, keyboard-accessible contextual/overflow menu. This still opens the suspended execution directly in the Session Editor **without activating or resuming its timer**, and editing retains its **Unterbrochen** status. Do not hide editing behind Resume. Exact icon/button sizing, focus handling, menu placement and mobile responsiveness remain for layout review.
- Use conflict-safe isolated drafts and explicit save/cancel behavior. Only commit a valid edit against the correct suspended execution state; preserve the frozen progress snapshot if saving fails or a conflicting update occurs. This introduces future offline editing of dormant run states; it is not implemented by existing single-context runtime recovery.

- **Discard current attempt** / **Durchlauf verwerfen** is distinct from **suspend** and **delete**. Following explicit confirmation, it clears the execution's run progress, recorded actual times/overtime and run-specific history, releases the timer and returns **the same individual execution** to **Geplant**, ready for an entirely fresh start. **Keep the latest configured planning state, including phase additions/removals/reordering, edited planned timeboxes and prepared notes/resources made during the run; do not silently revert to the initial Start baseline. Discard all separate execution-only Workshop-Notizen, even if they concern future phases.** Its original source template remains untouched. Resetting runtime statistics and separating run-specific observations from reusable planning content needs precise data-contract and recovery tests.
- **Delete** remains an explicit, separately protected library management action. Discarding an attempt **does not delete** the prepared execution. Do not treat suspension as workshop completion or append a suspended run to immutable completed history.
- Switching to a different execution while one is active must not silently replace/discard progress: the user needs a clear, intentional choice to suspend/save, discard/reset, or cancel the switch, with separately guarded completion if appropriate. Only release the old runtime after the requested state has been saved successfully; failures preserve the existing active execution and report the problem.
- **Explicit event ending is required (agreed UX):** An event/execution is over **only when the facilitator deliberately ends it**, not because a planned phase duration expires, the last phase ends, or the timer engine reaches its internal `run.stage === 'COMPLETED'`. **Ending and deciding whether to archive are distinct choices.** The user-visible library status **Abgeschlossen** is assigned only to an intentionally ended **and archived** execution. Until deliberate ending, existing final-overtime controls and the ET-001 possibility of extending an ended workshop with new phases must remain available as applicable.
- After the **first actual Timer Start**, offer a deliberate **end execution** entry point with the **three explicitly chosen retention options** documented in the following section. **Before that first Start (READY), archiving with results is not available; only retaining the prepared plan or discarding the individual execution is meaningful.** Ending the event, retaining its planning content, and archiving its measured results are distinct concerns. Only an archived execution becomes a read-only historical record, apart from its optional reflection field. Keep the choice concise rather than inventing a closure wizard; final microcopy, safe destructive-action confirmation, clock/overtime stopping, atomic persistence and recovery need later review. Ending must never occur implicitly on navigation or switching sessions. **Existing `Durchlauf verwerfen` resets an attempt to `Geplant` and is not synonymous with ending and deleting an individual execution.** A seven-second accidental Start must not force a meaningless archive record.
### Ending a run — three deliberate retention choices (agreed direction)

- At explicit **Durchführung beenden / End execution**, offer three clearly differentiated choices **only if this execution has had its first actual Timer Start**, with brief plain-language explanatory text; the following labels are **working copy, not fixed product wording**:
  1. **Mit Ergebnissen archivieren / Archive with results (only after actual first Start):** End the event and retain the complete, independently identifiable executed run in **Meine Durchführungen**, including its immutable start baseline, archived final state, actual phase times/outcomes, retrospective indicators, notes/resources and optional post-session reflection. It has status **Abgeschlossen**.
  2. **Nur den Ablaufplan behalten / Keep only the rundown plan (agreed):** End the event, **do not archive its measured results**, and retain **the same individual execution** under **Meine Durchführungen** with status **Geplant**. **Preserve the exact latest configured planning state**: phases added, removed or reordered during the workshop stay added, removed or reordered; updated planned timeboxes and prepared notes/links remain as currently configured. **Discard all notes captured separately during the run (Workshop-Notizen), whether attached to the current or a future phase:** they are execution content, not part of the retained planned Rundown. **Do not revert to the initial Start baseline and do not substitute measured IST durations for planned timeboxes.** Clear actual elapsed times, progress, phase outcomes, retrospective markers, and abandoned-run archive snapshots; the next actual Start establishes a new immutable baseline. Do **not** create a duplicate execution or new personal template, and leave any source template unchanged. Maintain the agreed distinction between plan notes and separate execution-only Workshop-Notizen in the future data contract; atomic reset/recovery needs tests. No new library tab or lifecycle status.
  3. **Ohne Speichern beenden / End without saving:** End and intentionally discard **the entire individual execution**, including its prepared/edited plan, **all notes attached to that execution (both prepared phase notes within its plan and notes captured during the workshop)**, links/resources stored only in it, and its measured progress/results. Create no archival record and leave no orphan individual execution in the library. **Any existing independent source template or previously archived execution remains unchanged.** Make this consequence explicit in the short option description; suggested working copy: **„Die Durchführung mit ihrer Planung, allen Notizen und Ergebnissen wird gelöscht. Bestehende Vorlagen bleiben erhalten.“** Avoid a separate notes decision or an extra closure step merely for this option.
- **Archive commits every started note draft (agreed):** When the facilitator explicitly chooses **Mit Ergebnissen archivieren** after the execution's first actual Timer Start, collect **all started but not yet explicitly saved Workshop-Notizen drafts**, both **Rundown-wide and across every phase**, regardless of which phase is current, whether its section is expanded, or where the writing focus currently sits. **Save their contents together with the execution's final archival state**; only after the whole archival operation succeeds may the execution become **Abgeschlossen**, its notes read-only, and the Facilitator Panel close. **No separate note-by-note save clicks or additional confirmation dialogs.** If any part fails, do not archive, close the panel or discard unsaved drafts; keep the execution and all input accessible with a clear error and retry option. This special **archive-with-results** behavior must not override the other end choices: **Nur den Ablaufplan behalten** intentionally discards all separate Workshop-Notizen, and **Ohne Speichern beenden** discards the entire execution. The same safety principle applies when archiving a suspended already-started execution from the library, without activating its clock.
- **Never-started READY exit (agreed clarification, not a new archive status):** Preparing/loading a session in READY is **not** an actual conducted workshop. If the facilitator ends it before the first real Timer Start, **do not offer "Mit Ergebnissen archivieren"**, do not create an **Abgeschlossen** record, a start snapshot, measured outcomes or a retrospective reflection. Offer only **Nur den Ablaufplan behalten** (the same individual execution returns to **Geplant**, with its latest prepared meta-information, phase information, links and planned timeboxes intact) or **Ohne Speichern beenden** (delete the entire individual execution and all its content). **Any separate Workshop-Notizen entered in the never-started READY context are discarded on either exit choice**; they do not survive as archived or historical observations. Show a brief clear hint, without a needless extra completion wizard, that there is no run to archive and that unsaved/execution-only notes will not be kept. Prepared information stored in the plan is **not** execution-only Workshop-Notizen and remains with the plan **only** if that plan is retained. The source template remains untouched. Closing the Panel normally earlier in READY may save drafts during that still-open execution, but must not override this later intentional deletion/retention decision.
- Provide a separate **Zurück zum Timer / Return to timer** cancellation path that changes nothing. These choices must not silently cause loss or implicit archival, and final destructive-action confirmation/keyboard/mobile UX is to be reviewed in one coherent flow, avoiding redundant dialogs.
- **Shared outcome with Durchlauf verwerfen (UX consolidation required):** **Nur den Ablaufplan behalten** and the previously agreed **Durchlauf verwerfen** both discard runtime progress and return **the same** individual execution to **Geplant** without archiving. Do not implement two competing reset mechanisms. Their wording/entry point may differ by context, but their planning preservation and data-safety semantics must agree. Distinguish both from **Ohne Speichern beenden**, which deletes the individual execution as well. Archiving results is not mandatory merely because the clock was ever started.
- The distinction between a newly started execution, a retained reusable plan, and an archived completed record must remain explicit in the two-tab library. No new timer, persistence or library implementation is authorized.

- **Facilitator-controlled ending (agreed):** **Once timekeeping has actually started at least once**, the facilitator may deliberately finalize a workshop **at any point**, including before all planned phases have been executed. **If a phase has already started**, explicitly finalizing the workshop simultaneously ends that phase and freezes its measured actual elapsed time, regardless of whether its clock was running or paused at that moment. The phase counts as **Durchgeführt / Conducted**, just like any other shorter-than-planned (or longer-than-planned) phase; do **not** invent a separate 'unfinished when workshop ended' phase status. Its deviation is calculated against its original planned duration at the execution's first actual Start. Phases **not yet started** remain **Nicht durchgeführt / Not conducted**, not completed. The act of finalization records the event's factual outcome and must not erase earlier phase statistics; exact atomic clock/snapshot implementation requires separate design and tests.
- **Agenda is adaptable until explicit finalization:** Even after **all originally planned phases have finished** and planned timeboxes have expired, the facilitator may add further phases (such as additional breakout rounds and a concluding discussion), and continue the same execution. Preserve earlier recorded progress/statistics. Follow the existing ET-001 decision 47: newly appended phases await explicit Start, final overtime is reset according to the accepted rule, and previous statistics remain; no implicit restart or automatic finalization. The exact handling of automatic transition mode and final-overtime clocks requires the later ST-003 runtime specification.
- **Three-layer conceptual model (agreed):**
  1. **Timer / timekeeping:** Measures and displays elapsed active time, remaining time and/or overtime for the relevant phase/session, starting with an explicit Start action and observing pauses and other defined timing rules. This layer answers **“Is time currently being counted, and how much?”** It does not own the event lifecycle.
  2. **Individual rundown / agenda:** The workshop's prepared and subsequently adapted phases, order, planned durations and notes, plus the recorded actual progress where applicable. This layer answers **“What was planned, what happened, and what remains?”** The original rundown represents the facilitator's planning assumptions at preparation time, **may be followed 1:1 when suitable**, and remains adaptable when the facilitator judges a change useful. **The facilitator decides how the actual workshop unfolds**, including changes to upcoming phases and additions after the originally planned end, until explicitly finalizing the execution; already completed phases and recorded history remain protected.
  3. **Execution lifecycle / library state:** **Geplant**, **Im Timer aktiv**, **Unterbrochen**, **Abgeschlossen**. This layer answers **“What is the status of this individual execution?”** Suspension, reset/discard and finalization are deliberate decisions with explicit consequences.
- **No automatic lifecycle transition from clock behavior:** Time not currently advancing (informally “gestoppt”) describes only the timekeeping layer and does **not by itself** mean the execution was suspended, discarded or completed. The clock can be paused while an execution remains **Im Timer aktiv**; a deliberately suspended or finalized execution likewise has no advancing time, but for a separately chosen reason. Phase/timebox expiry, stopping final overtime, and the timer engine's internal `COMPLETED` stage do not silently finalize the library execution. Some deliberate lifecycle operations necessarily freeze/release the clock, but never infer the lifecycle decision merely from a non-running timer.
- **Existing Stop terminology needs separate review:** In the released app, **Workshop stoppen / Stop workshop** performs `STOP_WORKSHOP` and resets to phase 1 after confirmation. This current implementation must not be mistaken for the three-layer product concept above. **No new “stop timekeeping only” button has been decided.** Later UX/copy work must distinguish the clock's own pause/stop/overtime controls from explicit **Unterbrechen & speichern**, **Durchlauf verwerfen**, and **Durchführung abschließen**, and preserve accepted ET-001 clock behavior unless separately reviewed and authorized.
- Storage, recovery/ownership, JSON compatibility and crash safety need explicit design and tests before implementation. The current single-context runtime recovery is **not** already a durable multi-suspended-execution library. This concept requires no account or cloud as a prerequisite.
- **Planned execution row actions (agreed hybrid UX):** For **Geplant**, show **Session starten** and **Bearbeiten** as the two directly visible actions, with **Session starten** the primary next step. Here **Session starten** means load this already planned, independent execution in the Session Timer at **READY**, **without starting its clock** or establishing its immutable start baseline; **Bearbeiten** opens the Session Editor directly without activating a timer. Put **Exportieren** and **Löschen** in an accessible context menu, with deliberate confirmation before deletion. Preserve discoverability, keyboard access and adequate touch targets on mobile and desktop; precise copy/placement is still subject to the visual layout review.
- **Active execution row action priority (conditional UX decision):** For **Im Timer aktiv**, **Zurück zum Timer / Zum Timer** is always the sole *essential* prominently visible action, because the Session Timer is the operational facilitation cockpit and the only place where an active run can be ended. **Prefer one visible action** with **Bearbeiten** available directly via an accessible context menu **if** this looks clear, balanced and significant in the actual desktop/mobile library layout alongside rows with two actions. If a lone action instead looks visually isolated, weak or inconsistent, allow **Bearbeiten** as a second directly visible action. This is intentionally a **visual UX acceptance decision**, not a mandatory two-button requirement; decide by reviewing the real UI at desktop/mobile breakpoints. In both layouts, Bearbeiten opens the Session Editor without pausing, restarting, or otherwise changing the active time measurement, preserving the separately agreed editing/concurrency safeguards. Do not add **Durchführung beenden** to the active library row or create cosmetic duplicate actions.
- **Other row priorities (agreed):** **Geplant** shows **Session starten** and **Bearbeiten** directly; **Unterbrochen** shows **Im Timer fortsetzen** and **Durchführung abschließen** directly, with **Bearbeiten** in the accessible context menu. The row's action weighting is state-specific; exact iconography, placement and final DE/EN labels remain part of the responsive layout review.


### Switching away from an active execution — explicit plain-language choices (agreed UX)

Identify the current execution by name and state that continuing with the new selection requires a decision about its current progress. Avoid opaque abbreviations, unexplained icon-only actions, and generic confirmation wording such as “Replace?”.
- Show each available action with its **full, descriptive button label** and a **short, smaller explanatory line directly beneath it**. Both belong together visually and semantically; the explanation must remain legible on narrow/mobile screens and available to assistive technology. Example German copy (refine DE/EN wording in the later copy review):

  - **Durchlauf verwerfen** — “Der aktuelle Durchlauf wird zum Startpunkt zurückgesetzt. Der bisherige Fortschritt wird verworfen; die geplante Durchführung bleibt erhalten.”

- Suspend/save and discard/reset are **distinct decisions**; neither is the same as pausing, completing, or deleting a rundown. Discard is potentially destructive: the user must make an unambiguous conscious choice, consistent with the explicit confirmation guardrail above. Whether a second confirmation is necessary or the fully explained selection itself suffices is a later interaction-design review, not a default to add extra dialogs.

- Keep option wording and descriptions more important than compactness or iconography. Exact controls/spacing, ordering, focus and keyboard interactions are to be tested against desktop/mobile; do not preselect the final widget or visual styling here.

### Completed executions — immutable record and one post-session note (agreed UX)

- A completed execution remains in the user's library as an **immutable record of its actual course**. Its phase sequence, recorded durations/overtime, prepared and run-time notes, links, and other execution history are **read-only after completion**; do not retroactively alter the documented workshop.
- **Archived notes remain in context and semantically separate (agreed):** In a completed execution's archive view, show each phase's **prepared information and resource links** together with its **Workshop-Notizen**, as **two distinctly labeled read-only sections in that same phase**, not consolidated into a note stream, relocated to a separate notes tab, or hidden behind extra navigation. **Empty archival sections, with a subtle no-notes cue (agreed refinement):** Render a labeled prepared-information, resource-link or Workshop-Notizen content section **only when it has actual content**; do not display empty headings, blank editable fields, or add-note actions in the immutable archive. **However, when a phase has no archived Workshop-Notizen, display one very small, subdued, italic informational line such as „Keine Workshop-Notizen zu dieser Phase erfasst.“** This deliberately confirms absence so a facilitator does not waste time looking for a note they thought they entered. It is **not** an empty editable notes section, button or alert, and it must not imply that prepared information or other note categories are also absent. **Keep the phase itself visible even if all of its optional content sections are empty**, so the historical agenda and outcome remain understandable. Apply the same content-sensitive rendering to Rundown-level prepared information and Workshop-Notizen, without hiding the execution or its phase structure. The same location/semantic distinction persists at **Rundown level**: archived prepared meta-information remains separate from archived Rundown-wide Workshop-Notizen. Content stays attached to its owning execution and phase, exactly as before completion; neither category can be edited after archiving. The **single separately editable post-session reflection** remains an execution-wide field and does not replace, merge with, or alter those frozen sections. Do not add a new archive notes manager merely to display this information.
- **Separate post-session reflection (semantic distinction and placement agreed):** Provide exactly **one optional reflection/annotation field per archived completed execution**, editable **after the execution has been deliberately completed**. Place it **directly on Rundown level, above the archived phase list**, under a clear and unmistakable heading such as **„Reflexion“** (working UI copy). Keep it visibly distinct from both archived prepared Rundown information and the archived Rundown-wide Workshop-Notizen; it is an independently discoverable place to add a retrospective note even when initially empty. This field is for retrospective observations and lessons learned *after* the workshop, and is **not** the same as the Rundown-wide Workshop-Notizen field used *during* an active or suspended execution. Both may concern overall workshop improvements, but their roles and editability differ: archived **Rundown-wide and per-phase Workshop-Notizen** are frozen as part of the historical record; the **post-session reflection** remains editable afterward. No per-phase post-session fields, note cards, or note-management system.
- **Reflection editing reuses the Workshop-Notizen interaction (agreed KISS):** At Rundown level in the completed archive, show existing reflection text in full read mode; if empty, show a subtle **„Reflexion hinzufügen …“** entry affordance. Tapping the text or affordance opens the same compact multiline editor pattern (approximately five/six visible rows, internal scrolling), with the same deliberately explicit actions **Speichern / Save**, **Verwerfen / Discard edits**, and **Löschen / Delete**. Do not introduce a different rich-text editor or additional note-management UI. **Do not carry over Panel-specific save-on-close rules to the archive**; those apply only to consciously closing the Facilitator Panel or collapsing its note-bearing phase. As elsewhere, avoid silently losing an unsaved reflection draft; detailed archive navigation/leave safeguards remain for implementation review.
- The post-session field keeps **one current saved value only**. Replacing or clearing it deliberately discards the previous content: **no per-edit version history, append-only log or restoration requirement** for this field. Standard explicit edit/save/cancel safeguards can be reviewed with the UI; no extra note-management feature is implied.
- The single current-value rule also applies to **user-editable templates**: saving deliberate edits replaces the existing template, without automatic per-save version history or rollback. Archived completed-run records remain independently immutable; editing a source template cannot retroactively alter them.
- **Reuse an archived execution (agreed):** A deliberately ended and archived execution must offer **Neue Durchführung erstellen / Create new execution** as a discoverable action. The facilitator chooses which historical representation becomes the basis of a **new, independent execution entity**: **(A) original prepared rundown at the first actual Start**, **(B) final configured rundown at archival**, or **(C) actual conducted course (IST)**. For **C**, include **only phases that actually ran**; omit removed and never-conducted phases, and turn **each phase's total actually measured active duration** into its new planned timebox, irrespective of intermediate timebox changes. This is a **fresh READY execution**, never a copy of the historical completed/timekeeping state. For A, B, and C, reset lifecycle, timer progress, outcomes, retrospective indicators and post-session reflection. The archived source remains completed and unmodified; the original source template remains unchanged. The new execution's own immutable baseline arises at its first actual Timer Start. Reuse must not automatically start its clock. Carry over appropriate reusable phase/rundown notes and links, not runtime statistics as records; precise fields, duration rounding/zero-time edge cases and option labels need separate data/UX review. Placement among archived row actions will be decided with the library action layout.
- **Completed execution row actions (agreed hybrid UX):** For **Abgeschlossen**, show **Ansehen / View** and **Neue Durchführung erstellen / Create new execution** as the two directly visible actions. **Ansehen** opens the immutable archived final-first view with its optional start-vs-final comparison and editable single post-session reflection field; it must not reactivate the historical execution or its clock. **Neue Durchführung erstellen** opens the already agreed choice among original Start plan, final configured plan, and actual conducted course, producing a fresh independent execution at READY without carrying over historical runtime progress. Put **Exportieren**, **Löschen**, and any deliberate **Vorlage aktualisieren / reusable content into source template** operation in a discoverable, accessible context menu. Any source-template overwrite requires an explicit, understandable confirmation; **no automatic template version history or rollback is planned**. Exact labels, action hierarchy, row layout, reflection placement and mobile/keyboard details require visual UX review; no runtime or storage implementation is authorized.

### Completed-execution archive: start and final states, not an audit trail — agreed direction

- **Precisely two planning snapshots per archived execution:** Capture an immutable **start baseline** at the moment of the **first actual Start of timekeeping in the Session Timer** for that execution; capture the **final state** when the facilitator deliberately selects **Durchführung abschließen** and **archives its results**. A never-started READY execution is **not eligible for archival** and has no fabricated start/final history. **Session starten** in the template/library only prepares the timer in READY and is **not** this baseline trigger. The baseline includes the individually prepared rundown as it stands at the actual first Start, not necessarily the original source template. Pausing, resuming, and suspending/returning must not overwrite that baseline. After a deliberately discarded attempt resets the execution to **Geplant**, a future new first Start establishes a fresh baseline; exact atomic persistence and reset rules need data-contract tests.
- **Default archived view is final-first, but meaningfully annotated (agreed, variant A):** Opening a completed execution is an intentional look back at its actual result, so this default view may be richer than the live rundown. Show the final agenda, actual phase outcomes/timings, edited notes/resources, and any phases **not conducted** although still planned when the facilitator ended the event. **Also show phases that existed in the start baseline but were deliberately removed during the execution**, as clearly subdued/struck-through historical entries labeled **Entfernt / Removed**. They are *not* part of the active final agenda and must never be portrayed as conducted. Subtle icons/indicators may mark modified or added phases, original-plan variance, and unperformed phases; the owner's suggested X/+/>> and colors are **illustrative only**, not approved iconography. Reserve the optional comparison for more detailed analysis, not as the only way to discover removed phases.
- **Skipped and never-started phases (agreed):** Use the **same factual archive result, Nicht durchgeführt / Not conducted**, for a phase deliberately bypassed during a workshop and one still planned but never started by the time the facilitator finalizes. Do **not** introduce a separate **Übersprungen / Skipped** outcome or require a reason. These phases remain part of the archived final agenda unless explicitly **removed** from it; **Entfernt / Removed** is a distinct case. A phase that was actually started counts as **Durchgeführt / Conducted**, including when its time was cut short by an explicit finalization. This decision defines archive semantics, not a new skip control or automatic transition behavior.
- **Optional comparison on explicit request:** Let the user reveal an **initial-plan vs. finalized-execution** comparison for learning and reflection. Changes in phase presence/order, titles, planned timeboxes, prepared notes, links, and recorded execution outcomes may be compared as supported by the data. Stable phase identities distinguish true additions/removals from edits or reordering. A deleted phase may no longer be present in the final rundown but remains identifiable from the immutable start baseline. Precise comparison presentation is a separate UX design decision.
- **Not a change log or version-control feature:** Do not store or display a sequence of intermediate planning edits, timestamps per edit, change reasons, or an audit timeline. Only the immutable start baseline, final state, and the separately required actual phase outcomes/timekeeping records are needed. They can reveal **what differs**, but not necessarily when or why an edit happened, nor any intermediate change later undone.
- **Optional learning context:** The existing **single editable post-session reflection field** can record the facilitator's voluntary reasoning or lessons learned; no required per-change explanation or new comment/version system. This deliberately limited execution comparison is independent of the separately confirmed **direct-overwrite semantics for user templates** if reusable planning content from a completed execution is explicitly applied to a source template.
- **Comparison baseline for elapsed-time variance (agreed):** For a conducted phase, the primary retrospective deviation is **actual elapsed active time minus the planned duration in the immutable Start baseline**—not versus a planned timebox edited during the run. Example: planned **15 min at Start**, later adjusted to **25 min**, actually **23 min**: label as **8 min longer than originally planned**. Do **not** automatically label those 8 minutes **Überzeit / overtime**: the phase finished 2 minutes before its latest adjusted 25-minute timebox. Planned-duration edits can be shown separately in the optional comparison, without reconstructing intermediate versions. The final indicators must distinguish the two concepts.
- **Phases added after the first actual Start (agreed):** A phase absent from the immutable start baseline but present in the finalized execution is labeled **Nachträglich hinzugefügt / Added during the workshop** (subject to final DE/EN microcopy review). If conducted, report its **total actual measured active duration** across that phase, regardless of any intermediate planned-timebox adjustments. There is **no original planned timebox for that phase at Start**, so never fabricate a retrospective +duration or a longer/shorter-than-original-plan variance for it. Its current/final configured timebox may be recorded as part of the final state, but is conceptually distinct from actual measured duration. If not conducted, mark that separately. This is derivable from the two snapshots and actual timer records; no phase-edit history, audit log or change reason is implied.
- **Retrospective wording for shorter phases (agreed):** A phase that actually took place retains its factual outcome **Durchgeführt / Conducted**, and may additionally show the automatically derived qualifier **Kürzer als geplant / Shorter than originally planned** when actual elapsed active time is below the planned duration captured at the execution's first actual Start. The deviation is informational, **not a separate lifecycle/phase status**, and needs no facilitator input. Avoid interpreting the cause or claiming that a goal was achieved early; do not substitute **vorzeitig beendet**, **schneller abgeschlossen**, or **verkürzt** as if they had the same factual meaning. Any important context or rationale belongs voluntarily in the already agreed notes/post-session reflection, not a mandatory per-phase reason field. Analogously show longer-than-planned variances without conflating them with technical overtime.
- **Snapshot limitation and presentation review:** A phase that existed at Start but was deleted afterward can be identified as **Removed** even without an edit log. A phase **added and then removed entirely between Start and finalization** appears in neither snapshot and **cannot be recovered or advertised as removed**. The two snapshots also cannot establish precise change timing or motives. Decide exact placement of historical removed entries, labels and iconography in a later mobile/desktop archive UX review. Distinguish clearly between **not conducted**, **removed**, **conducted (including the phase ended by event finalization)**, **actual elapsed time**, **original planned timebox**, **edited planned timebox**, and **overtime**, without reliance on color alone.

## 3. Contextual notes captured during facilitation — confirmed user-value case

**Concrete facilitator need (agreed):** During longer workshops, especially while a group independently works in a breakout, a facilitator may want to capture a spontaneous observation or reminder **about the current or a coming phase** in the same tool that holds the agenda and timekeeping. This avoids a context/tool switch to paper, PowerPoint presenter notes, Miro sticky notes or another note app, and allows the observation to be found later **in its workshop/phase context**. This need may be negligible for a short one-hour session but valuable over a full workshop day; do not impose note-taking on every run.

- **Workshop-Notizen structure (agreed): Exactly one editable, continuous note field for the entire individual execution (Rundown-level Workshop-Notizen), plus exactly one such field per phase** of that execution. Both exist for notes arising during facilitation, and the phase fields can be edited regardless of whether that phase is currently running or upcoming; do not model separate note cards, timestamps per entry, or a task list. The run-level field supports observations affecting the workshop as a whole **while the execution is ongoing**, for example: "Participants need a few more short breaks today because a production incident needs occasional checking"; it is not limited to the currently active phase. These execution-only fields are separate from the **prepared rundown-level meta-information** and from the prepared notes/links of each phase. The **one Rundown-wide Workshop-Notizen field is located in the top, default-collapsed Rundown area**, visibly distinguished from its prepared meta-information; the scrollable phase list below contains the single Workshop-Notizen field for each phase. This uses exactly **two main Panel areas**, with no extra third accordion and no second editor. Existing archival/discard rules apply equally to the run-level and phase-level Workshop-Notizen. The **separate post-session reflection** for a completed archive is **intentionally retained**: unlike during-run Workshop-Notizen, it captures retrospective additions **after completion** and remains editable while the archived Workshop-Notizen are read-only. Keep both single-field concepts distinct without introducing versions or extra note collections.

## 4. Architecture and scope guardrails

- Preserve one authoritative timer state and existing Session Timer behavior.
- Maintain the distinction between the saved Rundown definition, the active run's snapshot, and notes captured during that run.
- New persisted Rundown data must be designed and tested with Schema-2 storage, strict validation, new-model JSON import/export and recovery. Existing released functionality and the isolated optional Google synchronization work must not be accidentally broken. This regression boundary does not require V1-to-V2 data migration.
- **JSON field naming (distinct from UI copy):** The released Rundown implementation still uses **`schemaVersion: 1`** and phase records with **`id`**, **`title`**, and **`durationSeconds`**. EDITOR-001 instead uses the approved native Schema-2 contract, including neutral prepared `notes`, resources and separate execution `workshopNotes` associated with stable phase identities. New-model JSON portability and recovery require their own explicit integration and tests; they must not become a historical V1 conversion path. Displaying prepared content to an audience remains a presentation choice, not a field-level security promise.
- No own backend, database, account system, file hosting, or mandatory Google login for the initial increments.
- No new confidentiality, roles, or access-control system in this initiative.
- Cross-device **live timer synchronization** is a separate, strategically important feature and takes priority over private notes or role-gated views. Google identity alone must not be mistaken for live state synchronization.
- Future Miro embedding/integration is out of scope.

## 5. Candidate incremental delivery path (not yet approved)

1. **Concept and data contract:** use native Schema-2 templates and independent executions, validate new-model storage/JSON behavior, and preserve the active-run snapshot boundary. No historical V1 compatibility migration is required. Treat data-model changes as higher-risk than cosmetic UI work.
